# 二 提纲与字段设计

## 目的

把研究问题拆成一张「对象乘字段」的矩阵。行是要查的对象，列是要填的字段。矩阵的价值在于可清点：查了几个、缺几项、哪一格是空的，一眼可见。

## 对象清单的三种列法

穷举法：适用于对象边界清楚的情形，如全部市级医院、全部区级统战部门。先列全量名单，再按相关性排序。

维度法：适用于对象边界模糊的情形。先定两三个切分维度，例如按机构层级、按品牌类型、按时间阶段，再从维度交叉处取代表。

滚雪球法：适用于陌生领域。先找三到五个已知对象，读其材料中反复出现的其他对象，迭代补充，直到不再出现新名字。

三种方法可以混用。无论用哪种，对象清单要能回答「为什么是这些、为什么不是别的」。

## 对象粒度

一个对象应同时满足两条：可以独立检索到材料；可以在报告中独立成段。太粗，如「各级医院」，无法检索；太细，如「某院某次活动」，撑不起一段。

## 字段设计四条原则

第一，可核验。字段值应能指向一个链接、一个文号或一组数据。写「影响力较大」不可核验，写「覆盖 12 个社区、年服务 3000 人次」可核验。

第二，口径统一。同一字段在不同对象上必须同义。若某对象没有对应口径，标 `[不确定]`，不要换一个近义指标凑数。

第三，详细度分层。用 detail_level 三档：极简用于标识类信息，简要用于判断类信息，详细用于机制与证据类信息。

第四，数量克制。单对象字段控制在八到十五个。超过十五个，填充率必然下降，且大部分字段不会进入报告。

## outline.yaml 结构

```yaml
topic: 调研主题
items:
  - name: 对象名称
    category: 对象分类
    description: 一句话说明为何纳入
execution:
  batch_size: 每批并行子任务数
  items_per_agent: 每个子任务负责的对象数
  output_dir: ./results
```

## fields.yaml 结构

校验脚本只接受这一种格式，其他形状会直接报错，不会静默通过。

```yaml
fields:
  分类名:
    - name: 字段名
      description: 口径说明
      detail_level: 极简 | 简要 | 详细
uncertain: []
```

若某字段可缺省，显式写 `required: false`；不写则视为必填。

## 示例

见 `templates/outline.example.yaml` 与 `templates/fields.example.yaml`。示例以医院统战工作品牌为主题，覆盖基本信息、制度与依据、做法与机制、成效与证据、争议与局限五类字段。

## 确认点

对象数与字段数在进入深挖前必须由用户确认，尤其是 batch_size 与 items_per_agent。默认值建议 batch_size 为三、items_per_agent 为一，宁可多批，不要一次铺开。

## 反模式

对象太粗，检索不到材料。字段太抽象，填出来全是形容词。字段太多，填充率不足三成。对象与字段没有对应关系，例如给政策文本配「用户规模」字段。直接把模型生成的框架当最终版，不向用户确认。
