# 三 逐项深挖与字段校验

## 前置检查

进入本阶段前确认三件事：`{topic}/outline.yaml` 与 `{topic}/fields.yaml` 存在；字段格式通过校验；用户已同意本批的对象数。

## 分批与断点续传

按 batch_size 分批，每批完成并经用户同意后再开下一批。开跑前先扫描 output_dir，已存在且通过校验的对象直接跳过，实现断点续传。

批大小的选择看两点：对象材料密度与单次可承受的检索量。材料密度高的对象，一批只放一个。

## 单个对象的提示词

以下提示词原样交给子任务，只替换变量。

```text
## 任务
调研 {item_related_info}，输出结构化JSON到 {output_path}

## 字段定义
读取 {fields_path} 获取所有字段定义

## 输出要求
1. 按 fields.yaml 定义的字段输出 JSON
2. 不确定的字段值标注 [不确定]
3. JSON 末尾添加 uncertain 数组，列出所有不确定的字段名
4. 所有字段值必须使用中文输出（调研过程可用英文，但最终 JSON 值为中文）

## 输出路径
{output_path}

## 验证
完成 JSON 输出后，运行验证脚本确保字段完整覆盖：
python {validator_path} -f {fields_path} -j {output_path}
验证通过后才算完成任务。
```

变量说明：`{item_related_info}` 为对象的完整 yaml 内容；`{fields_path}` 为 fields.yaml 的路径；`{validator_path}` 为本仓库 `scripts/validate_json.py` 的路径，不便引用绝对路径时复制到当前目录；`{output_path}` 为 `{output_dir}/{对象名}.json`，对象名中的空格替换为下划线，去掉特殊字符。

## 子任务派发

有并行能力时按 batch_size 并行派发，没有则串行。两种方式的产物结构一致，串行时在交付末尾注明「本次为串行执行」。

子任务只做检索与填表，不再向下派发子任务。递归扩张会迅速放大成本，且中间层丢失上下文。

## 不确定值的处理

三种情况标 `[不确定]`：检索不到；来源互相矛盾且无法判断；字段口径与对象不匹配。

不要用「据估计」「大致」这类词替代 `[不确定]`。含糊表述会让汇总阶段误判为有效值。

## 完成判定

以文件为准，不以日志为准：JSON 存在、字段覆盖通过校验、uncertain 数组已填写，三者齐备才算完成。

## 反模式

一次把所有对象铺开，中途失败无法续跑。跳过校验直接汇总，缺字段在报告里变成空白。把检索摘要当原文填入，未核对发布主体。子任务递归派发。用推测值填补缺口而不标注。
